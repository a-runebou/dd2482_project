# Frontend Decisions

F1 Package manager and runtime: npm and Node 24 LTS, pinned by `.nvmrc` and enforced by engines with engine-strict.

F2 Router: React Router, chosen for the fewest moving parts and no route code generation.

F3 Runtime API client: openapi-fetch, typed by the generated paths type; its middleware is the place for the bearer token and refresh-and-retry-once.

F4 Mocking: MSW, in Vitest and optionally in development, because it can script 304, 503 db_circuit_open with Retry-After and token_expired.

F5 Layout: hand-written API code in `src/api/`, generated types in `src/api/generated/`, generated output committed and verified by check:api.

F6 (provisional) API base URL: relative `/api/v1` by default, overridable at build time through `VITE_API_BASE_URL`; runtime configuration for the deployed image is undecided and depends on the CORS and origin question. Note: the resolver takes an explicit origin (`resolveBaseUrl(configured, origin)`) and the client passes `globalThis.location.origin`, because Node's `Request`, used by the Vitest jsdom environment, cannot parse a bare relative URL; in a browser this is equivalent to the relative default.

F7 Error model: `ApiError` kinds `problem`, `network` and `unexpected`; UI code switches on `code` only for kind `problem`, and a code outside `ErrorCode` is never cast, it is `unexpected`.

F8 Routing and boot: React Router data router in library mode, with no loaders or actions for server data. Routes render only after GET /config succeeds; boot failures are full-page states chosen by ApiError kind and code, with automatic retry only when Retry-After was readable.

F9 Source layout: src/api for data access, src/app for the shell (providers, routes, boot gate, error boundary), src/pages for route-level components. The layout for feature code is decided when the first feature lands.

F10 Development mocking: an MSW browser worker runs only in development and only under vite --mode mock (VITE_API_MOCKING=enabled). Handlers are shared with tests and match the real base URL. The production bundle contains no MSW code; the generated worker file is copied to dist but never registered.

F11 Dates: user-facing dates format in en-GB; calendar dates from the API (YYYY-MM-DD) are formatted as calendar dates and never converted through an instant or the browser's timezone.

F12 Feature layout: feature code in src/features/<feature>/ (query options, hooks, components, colocated tests), shared presentational components in src/components/, framework-free pure helpers in src/lib/, thin route components in src/pages/; query keys start with the feature name.

F13 Development API proxy: the Vite dev and preview servers forward `/api` to `http://localhost:8000`, the contract's local server, so the browser talks to a single origin in development, matching the single-origin proposal in item C1 of `docs/coordination/frontend-backend.md`.
F14 Group creation form: the timezone is preselected from the browser when `Intl.supportedValuesOf("timeZone")` contains the resolved zone, otherwise the contract default `Europe/Stockholm`, which is always present in the options so the preselection is selectable. The daily window is offered as 24-hour labels over minutes from local midnight, in steps of `config.slot_minutes` from `GET /config`, defaulting to 08:00 to 18:00, with the final end option labelled "24:00"; a label is a rendering of a minute offset, never a wall-clock instant. An `Idempotency-Key` is generated per distinct serialized body with `crypto.getRandomValues` (never `crypto.randomUUID`, which needs a secure context) and reused only when resubmitting identical values, so a retry after a failure is the same request and an edit is a new one. UX validation covers only a non-blank name, both dates present, the date order, the configured range limit and the window order; the schema's length limits belong to the backend and are surfaced through `errors[]`. Copying the invite link never relies on the clipboard API alone, because the development VM has no TLS (ARCHITECTURE R1): a missing or rejecting `navigator.clipboard` selects the field and shows the keyboard shortcut. `invite_url` exists only in component state, never in web storage, a URL, the query cache or the console, so the creation response is deliberately not seeded into the cache.

F15 Frontend image: a multi-stage build producing an nginx image that serves the static bundle and proxies `/api` to `BACKEND_ORIGIN`, substituted at container start. The application and the API therefore share one origin in every environment, which is the single-origin topology proposed in item C1. The image bakes in no API URL, so `VITE_API_BASE_URL` is not used in deployment and F6 needs no runtime mechanism.

F16 Sign-in request: the e-mail exists only in component state and is never persisted anywhere. The confirmation after a 202 deliberately reveals nothing about whether the address has an account, matching the contract's reason for always answering 202. redirect_path is not sent until item C2 is settled.

F17 Session storage: the access token and the user live in a module-level store in memory, observed with `useSyncExternalStore`. No storage API is ever used, per CLAUDE.md rule 10, and the token is kept out of the query cache as well: the exchange and probe queries resolve to a boolean, never to the `SessionResponse`. A page reload restores the session only through the HttpOnly refresh cookie, by way of a boot probe that gates the root layout alongside `GET /config`; being signed out is one of the probe's two normal outcomes, so it has no failure state.

F18 Refresh: one refresh at a time per tab, through a shared in-flight promise, and across tabs through the Web Locks API when `navigator.locks` is present, falling back to per-tab serialisation when it is not. A 401 with code `token_expired` triggers exactly one refresh and one retry; the retry re-sends a clone of the original request through the raw fetch, so it cannot re-enter the middleware and a second 401 is surfaced unchanged. Any other 401, and a refresh that itself fails, clears the session. `/config`, `/auth/magic-link`, `/auth/session` and `/auth/refresh` neither carry the bearer token nor trigger a refresh. This complements the backend grace window agreed in item C3. `credentials: "include"` is set on the client rather than in the middleware, because `Request.credentials` is read-only once the request is constructed.

F19 Callback: `/auth/callback` exchanges the magic-link token once and replaces the history entry, so going back cannot resubmit a spent token. The exchange is a query rather than a mutation precisely for that "once": a query is deduplicated per `QueryClient`, so StrictMode's double effects and a remount share one request. A `redirect` parameter is honoured only when it is a path relative to this origin — one leading slash, no second slash, no backslash — per item C2; anything else lands on `/`. A token that is invalid, spent or expired (`unauthenticated` or `validation_failed`) shows one wording that does not distinguish the three, and the token itself is never rendered.

F20 Visual design: the direction is quiet and utilitarian — warm neutrals, one accent, hairline borders rather than shadows, whitespace instead of decoration. The whole token set is declared with Tailwind v4's `@theme` in `frontend/src/index.css`, which is the configuration: there is no `tailwind.config.js`. It is five warm neutrals plus white, one accent with a hover and a subdued wash, one danger colour, five type sizes with line heights, two weights, three radii and two shadows; spacing stays on Tailwind's default scale. Every colour is defined there and referenced through a token, so a raw hex value in a component is a bug, checked by `grep -rnE "#[0-9a-fA-F]{3,8}\b" src --include="*.tsx" --include="*.ts"` returning nothing. The primitives in `src/components/` — Button, Field, TextInput, Textarea, Select, Card, PageContainer, PageHeading, Spinner — are what screens are built from; a screen does not reach for an ad hoc utility class where a primitive exists. Field owns the id generation and the `aria-describedby` and `aria-invalid` wiring, so a form never does that itself. One focus treatment, a 2px accent outline with an offset, is shared by every button, control and link. There is no component library and none may be added, and there is no dark mode: the palette is defined on `:root` with no `prefers-color-scheme` branch.

F21 Group detail: the group and its members are separate queries so one failing does not blank the other. Mutations send If-Match from the ETag of the last read, and a 412 version_conflict offers a refetch without discarding input. Destructive actions require an explicit confirmation, with deletion of a group additionally requiring the name to be typed. A rotated invite link exists only in component state, as on creation. The ETag is cached beside the body it validated, as `{ group, etag }` under `["groups", "detail", slug]`, rather than in a ref or a module variable: a refetch replaces both at once and nothing can survive a refetch and go stale. It is not rebuilt from `Group.version`, because the contract calls the validator "derived from the group version" and defines no derivation, so the opaque bytes the server sent are what go back. The members key is nested under the detail key, so every invalidation of the group alone is `exact`, and deleting a group removes both entries instead of refetching a slug that now answers 404. The one place the two queries are not independent is a not-found group: the whole screen becomes the not-found panel, because a roster rendered beside "Group not found" would disclose more than the backend's deliberate 404 is willing to.

F22 Availability grid: slots are generated per local day in the group's timezone, so the 25 October 2026 daylight-saving change yields the correct number of slots — a local day is 23 or 25 hours long and adding a fixed day length drifts by an hour and then stays wrong (ARCHITECTURE R7). Each day's window start and window end are resolved to instants independently and the slots between them are stepped in UTC, which keeps every slot exactly `slot_minutes` apart in real time while the local labels repeat an hour in the autumn and skip one in the spring. A wall-clock time is resolved by taking the zone's offsets a day either side of it, which are the only two it can have: two candidates survive for a repeated hour and `earlier`/`later` picks between them, none survives for an hour the spring change deletes and the window edge rolls forward. `lib/slots.ts` is pure, takes its timezone explicitly everywhere, and uses `Intl` with an explicit `timeZone` rather than `new Date`, so the browser's own zone cannot leak in; its tests run with the process timezone stubbed to `Pacific/Auckland` to prove it. The server's `slots` vector is authoritative for rendering and the generated one is only ever compared against it; a disagreement is surfaced as a non-blocking notice rather than hidden, because a silent difference between the two is exactly the bug this arrangement exists to catch. Selection lives in component state until saved, writes are a full replacement per CLAUDE.md rule 9 — modelled as one map from instant to state, so "a slot in both arrays counts as preferred" is true by construction rather than by a rule applied at the last moment — and the write's own response, not the refetch it triggers, becomes the new baseline, so a refetch that fails or arrives late cannot seed a stale read over a successful save. Busy blocks are a visual hint that never restricts selection (ARCHITECTURE 6.2). The heatmap weighting is `(available + 2 x preferred) / (2 x responded)`, with members who have never responded excluded from the denominator as the suggestion scoring excludes them (ARCHITECTURE 5.1), conveyed by five shades of the one accent at different opacities — the palette is closed (F20), so no new colour was added — and never by shade alone: every cell's accessible description states the counts and names the available, the preferring and the missing members. The grid is a roving tabindex over `role="grid"`: one cell is in the tab order and the arrow keys move between them, rather than several hundred tab stops. Pointer interaction is `pointerdown` plus `pointerover` and nothing else, and the keyboard is `keydown` with the default prevented, because a browser fires `pointerdown` and then `click` for one press and handling both would cycle a cell twice; a press decides the state the first cell is moving to and every cell the pointer then crosses is set to that state, so a drag paints a region rather than cycling each cell. The release is watched on the window, so letting go outside the grid ends the drag cleanly. `slot_minutes` is read from the group rather than from `GET /config`, because the contract carries it on `Group` and a group is what the window belongs to.
